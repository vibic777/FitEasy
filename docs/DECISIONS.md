## D132 — порт этого устройства: автоматически или вручную, с проверкой «свободен / занят»

11.10.2026, указание vibic777: порт для соединения должен задаваться и вручную; по умолчанию — автоматически; писать, занят порт или нет.

- По умолчанию «Автоматически», как было: обычный порт 47821, а если он занят — любой свободный; другое устройство находит порт само. Теперь страница пишет, какой порт взят, и отдельно — что обычный занят другой программой и взят свободный.
- «Вручную»: порт от 1024 до 65535 (ниже — порты системы, телефон их открыть не может). В окне выбора порт проверяется через треть секунды после ввода, вне потока интерфейса: «свободен», «занят другой программой», «сейчас использует это приложение». Сохранить можно только свободный порт или тот, на котором приложение уже ждёт.
- Заданный вручную порт — единственный, который пробуется: человек открыл в брандмауэре именно его. Если он занят при следующем запуске приёма, устройство не принимает синхронизацию и пишет об этом красным с подсказкой выбрать другой порт или «Автоматически»; молча другой порт не берётся.
- Порт хранится в настройках синхронизации устройства (секрет устройства, Keystore / DPAPI), в данные, копию и передачу не попадает. После сохранения приём запускается заново.
- Безопасность не меняется (сверено с docs/SECURITY_REVIEW.md, пункт 6): приём по-прежнему только из локальной сети и только пока открыта страница или включён постоянный приём; защита — код пары и шифрование, а не номер порта.
- Фоновая работа не менялась. Общий код Android и Windows; тексты, подсказки и абзац справки — на десяти языках.

## D130 — проверка безопасности кода и библиотек: четыре исправления

11.10.2026. vibic777: проверить весь код на безопасность — что не использованы опасные библиотеки и что телефону не добавлены уязвимости.

Что проверено чтением кода: манифест и компоненты Android, права, намерения и отложенные намерения, хранение ключей (Android Keystore, Windows DPAPI), шифрование базы и копий, блокировка приложения и восстановление, синхронизация по локальной сети (рукопожатие, шифрование, приём данных), почтовый клиент, импорт файлов (копия, файл базы, мелодия, фон), журнал, единственный экземпляр и установщик Windows. Версии всех библиотек обеих платформ (121 версия, с транзитивными) сверены с базой уязвимостей OSV — известных уязвимостей нет.

Исправлено:

- Мелодия напоминания открывается только из своих мест. Адрес мелодии хранится в данных и приходит также из импортированного файла базы. Раньше телефон открыл бы любой адрес, в том числе сетевой (обращение к чужому серверу при срабатывании напоминания), а Windows — любой путь, в том числе сетевой `\\компьютер\папка` (Windows при этом входит на названный компьютер под учётной записью пользователя). Теперь Android принимает только звуки системы (`content://`) и файл из своей папки `reminder_sounds`, Windows — только папку звуков Windows и свою `reminder_sounds`; сетевой путь не трогается вовсе. В остальных случаях играет системный звук. По синхронизации адрес мелодии и раньше не передавался.
- Данные приложения не уходят с телефона средствами Android: к `allowBackup="false"` добавлены правила `dataExtractionRules`, исключающие всё и из облачной копии, и из переноса «с телефона на телефон». На Android 12+ один `allowBackup` перенос между телефонами не запрещает. Ключи остаются в Keystore старого телефона, поэтому перенесённая копия всё равно не открылась бы. Дневник переносится способами, которые выбирает человек: копия, файл базы, синхронизация.
- Чужой файл базы читается с `PRAGMA trusted_schema=OFF`: его представления и триггеры не могут вызывать ничего, кроме обычного SQL. На Windows файл и раньше открывался только для чтения запросов, на Android — только для чтения.
- Пока включена блокировка приложения, окно на Android скрыто от снимков, записи экрана и картинки в списке недавних приложений (`FLAG_SECURE`), как в Notio. Раньше при включённой блокировке последняя открытая страница была видна в списке недавних приложений. Подсказка на странице «Защита и приватность» и абзац справки — на десяти языках.

Оставлено как есть, с причиной:

- Устройство, с которым создана пара, может прислать данные без вопроса, если на нём все три выбора соединения заданы заранее (D111, D116), — в том числе замещение. Это решение владельца; пара создаётся по коду и хранит общий ключ, но потерянное или чужое спаренное устройство нужно удалять из списка.
- Шифрование базы по умолчанию выключено (решение владельца): файл базы лежит в закрытой папке приложения открытым. Блокировка приложения — преграда на экране, а не шифрование.
- Экран будильника поверх блокировки показывает название и комментарий напоминания независимо от настройки «что показывать на экране блокировки» — так задумано в D086, включается отдельно. Вопрос владельцу: применять ли к нему ту же настройку.
- Почта «без шифрования» передаёт пароль открыто — доступна только после предупреждения и подтверждения.
- Библиотеки звука Windows (mp3spi, jlayer, tritonus-share, jorbis) давно не обновляются. Они написаны на Java (ошибка разбора даёт отказ, а не порчу памяти), читают только файл, выбранный человеком, и в телефон не входят.
- APK подписаны тестовым ключом Android Debug; перед публикацией нужен отдельный ключ (пункт в RELEASE_CHECKLIST.md).
- Мелкое: строка ответа почтового сервера и разбор принятой при синхронизации передачи (до 64 МБ целиком в памяти) не ограничены жёстче — отправитель в обоих случаях выбран самим человеком.

## D127 — «Права» в настройках: выдача и отзыв в одном месте

11.10.2026, указание vibic777: вкладка «Права» в меню; вынести туда (задублировать) выдачу всех нужных прав и разрешений, отзыв каждого права и отзыв всех прав.

- Новый пункт меню настроек «Права». Для каждого права: название, для какой функции оно нужно, выдано ли, и одно действие по состоянию — «Разрешить» либо «Отозвать». Прежние места, где права просятся по ходу дела («Напоминания»), оставлены: страница их повторяет.
- Android, четыре права: уведомления, точные напоминания, экран будильника поверх блокировки, показ поверх других окон. «Разрешить» — тот же путь, что и раньше: системный запрос либо страница системы.
- Отзыв. Android позволяет приложению самому отказаться только от прав, выдаваемых запросом; у FitEasy такое одно — уведомления (`revokeSelfPermissionOnKill`, Android 13+), отказ вступает в силу, когда приложение закроется. Остальные три выдаёт и забирает только человек на странице системы — «Отозвать» открывает именно её. Страница говорит, какой из двух случаев произошёл.
- «Отозвать все права»: приложение отказывается от уведомлений и открывает страницу приложения в системе, где выключается остальное; перед этим подтверждение с тем, что перестанет работать. Данные не удаляются. Эта кнопка названа словами, а не значком — отступление от правила значков: одинокий значок «стоп» не говорит, что забирается всё.
- Ниже перечислены права, выдаваемые при установке и не отзываемые по одному (сеть для синхронизации, вибрация, будильники после перезагрузки, биометрия, служба мелодии), и сказано, чего у приложения нет: контактов, местоположения, камеры, микрофона, файлов. Тест сверяет это с манифестом.

- Батарея (docs/BATTERY.md): страница не опрашивает систему — состояние читается при открытии и при возвращении приложения на экран. Запроса на выход из оптимизации батареи по-прежнему нет (правило 11).

## D125 — запись базы в своём потоке, с подтверждением

10.10.2026, по открытым пунктам TODO «вынести запись в фоновую очередь с подтверждением сохранения» (D080, D102). Автономное решение.

- Сохранение делится на две части. Проверка значений и замена состояния в памяти выполняются сразу, в вызвавшем потоке: неверное значение отклоняется немедленно, как раньше, а следующее чтение уже видит новое. Запись на диск выполняет один отдельный поток (`SaveQueue`, общий код).
- Поток пишет всегда относительно того, что точно лежит на диске, поэтому по-прежнему уходят только изменённые строки. Состояния, пришедшие за время одной записи, объединяются: пишется последнее.
- Подтверждение: `flushSaves()` ждёт, пока всё переданное окажется на диске, и говорит, удалось ли. Он вызывается перед переименованием и заменой файла базы (шифрование, обнуление), при закрытии программы на Windows и при уходе приложения с экрана на Android (`onStop`) — после этого система вправе завершить процесс в любой момент.
- Отказ диска: состояние в памяти возвращается к тому, что лежит на диске, интерфейс перечитывает его и показывает «Последнее изменение не записано на диск…» на десяти языках; после отказа о содержимом файла ничего не предполагается — следующая запись сверяется с самим файлом.
- Проверка дневника больше не перечитывает уже проверенные записи: запись одной строки проверяет одну строку.
- Замер (`SaveSpeedTest`, 20 000 записей и 300 заметок): новая запись в потоке интерфейса 39 → 3,5 мс, переключатель 4 → 0,1 мс.
- Цена решения: если процесс убит в те миллисекунды, пока запись ещё в очереди и приложение на экране, последнее изменение теряется. Раньше в этом случае обрывалась незавершённая транзакция — результат тот же.
- Формат базы, LAN 7, Transfer 5 и backup 5 не менялись.

## D122 — установка Windows: файлы программы не теряются молча

10.10.2026, по открытому пункту TODO (из Notio, Windows D91). Папки D:/Notio на этой машине нет, сделано по описанию в TODO.

- Установщик пишет `REINSTALLMODE=amus`: при обновлении каждый файл записывается заново, а не только изменившиеся. Иначе удаление старой версии, отложенное до перезагрузки, могло стереть библиотеки, которые новая версия сочла неизменными.

## D119 — фигура упражнения остаётся целой; виды с обоих боков и сверху

08.10.2026, замечания vibic777: после настройки упражнения в редакторе каркаса и перевода в силуэт руки оторваны от плеч — конечности не должны отрываться ни в скелете, ни в силуэте, это целый человек; добавить вид с другого бока и вид сверху.

Причина отрыва. Плечи ставились рядом с грудью по осям сцены: левое — левее, правое — правее, на одной высоте. Пока туловище стоит прямо, это верно. Когда грудь наклонена или туловище лежит, линия плеч оставалась горизонтальной, а силуэт туловища рисовался вдоль наклонённого позвоночника с шириной поперёк него: плечо оказывалось за краем туловища, рука — отдельно. В скелете ключица тянулась до плеча и разрыв был не виден. Второй случай — туловище, обращённое к зрителю торцом (лежащая фигура с ног, наклон вперёд при виде спереди): контур туловища сжимался в полоску, а руки и ноги оставались на своих местах.

- Плечи держатся на грудной клетке в её собственных направлениях (поперёк, вдоль позвоночника, вперёд) и наклоняются вместе с ней. Прямо стоящая фигура и встроенные упражнения не изменились ни на точку — проверено тестом; меняются только позы с наклонённым туловищем, где плечи раньше стояли неверно. Бёдра остались рядом с тазом по осям сцены: таз при наклоне груди не наклоняется.
- Силуэт: плечи, бёдра и шея соединены с туловищем перемычками своей ширины, нарисованными под ним. В обычной позе туловище их закрывает, рисунок прежний; при наклоне, растяжении или виде с торца они удерживают руку на плече и ногу на бедре. Скелет: шея доходит до позвоночника, каждое бедро — до таза, череп — до шеи.
- Туловище и голова, видимые вдоль своей оси, рисуются как вид сверху или снизу: плечи в одежде и бёдра, макушка с носом впереди.
- Виды. Кнопки редактора: спереди, сбоку, с другого бока, сзади и сверху. Вид сверху — наклон сцены на 90° (RigPose.pitch, −90…90, по умолчанию 0), он сохраняется в позе, как и поворот, и плавно меняется между кадрами. Перетаскивание суставов и предметов в наклонённом виде идёт в плоскости экрана. Отвергнут вид сверху как временный режим только редактора: тогда упражнение нельзя было бы показать сверху при выполнении.
- Проверка «целый человек» — автоматическая: рисунок каждой из шестнадцати трудных поз обязан быть одним связным пятном.

Поле pitch необязательное, версии форматов не менялись. Это рисунок, а не анатомическая модель: при сильном скручивании возможны неестественные, но связные формы.

В выбранных разделах принимающее устройство получает ровно то, что прислано; остальные разделы не меняются. Границы разделов те же, что при передаче: питание — записи еды и приёмы пищи; напитки, активность (плюс тренировки и свои упражнения), замеры; каталоги — продукты, блюда, избранное; рецепты; профиль; цели с историей и расчётами; расписания; заметки с папками; напоминания. Продукт или блюдо, на которые ещё ссылается оставшаяся здесь запись или рецепт, при замещении каталога не удаляются; продукты, нужные принятым записям, добавляются. Со всеми разделами результат прежний. Правило D111 действует: при заданных заранее трёх выборах второе устройство не спрашивает и для выборочного замещения. Протокол LAN 7 и Transfer 5 не менялись: устройство до 0.4.29 такой запрос отклоняет до передачи данных, ничего не меняя.
- Напоминания получили время изменения Reminder.updated (0 у созданных раньше); его ставят сохранение формы и выключатель напоминания. Слияние берёт напоминание, изменённое позже, — раньше оно только добавляло недостающие, поэтому правка на одном устройстве до второго не доходила, а итог сообщал об успехе. Мелодия остаётся своей у каждого устройства и при обновлении, и при замещении. Удаление напоминания слиянием не передаётся (отметок удаления у напоминаний нет) — для этого служит замещение раздела «Напоминания». Отметка демонстрации считается без нового поля, чтобы демо-напоминания прежних версий по-прежнему узнавались.
- Итог синхронизации говорит словами, когда слияние ничего не изменило, и подсказывает замещение. Профиль и цели при слиянии по-прежнему берутся, только пока на устройстве значения по умолчанию; сделать их такими же, как на другом устройстве, теперь можно замещением этих разделов.

Причину «сообщает об успехе, но ничего не меняет» воспроизвести как сбой передачи не удалось: движок с заданными заранее выборами проходит проверку на двух установках в обе стороны. ## D102 — скорость и плавность: отрисовка Windows, запись только изменённого, кеш переводов

05.10.2026, замечание vibic777: Windows-приложение подтормаживает в сравнении с Notio. Измерено и найдено три причины.

1. Окно по умолчанию рисовалось программно (skiko.renderApi=SOFTWARE_FAST, режим совместимости для виртуальной машины из 0.3.2), тогда как Notio оставляет выбор библиотеке и получает Direct3D. Запись по-прежнему выполняется в потоке интерфейса: вынос в фоновую очередь требует развязать подтверждение сохранения и закрытие диалогов и остаётся отдельной задачей; после п. 2 её цена — десятки миллисекунд на очень большой базе.

Аппаратные датчики шагов регистрируются с пакетной задержкой 60 с вместо 5 с; при включённом экране служба вызывает flush каждые 5 с, поэтому интерфейс не отстаёт, а при выключенном экране телефон будит сам датчик. Запись пачки: 2 с при включённом экране, 0,5 с для аппаратной пачки и 30 с для программного режима при выключенном. Программный режим после 3 минут без шагов снимает акселерометр и wake lock и ждёт TYPE_SIGNIFICANT_MOTION либо включения экрана; без такого датчика остаётся прежняя постоянная работа. Уведомление шагомера при выключенном экране не обновляется.

Пересмотр пункта D-052 «не держать открытые соединения»: Android и Windows держат одно соединение SQLCipher на время процесса. Причина: каждое открытие шифрованной базы заново выводит ключ (PBKDF2, 256000 итераций) и обращается к Keystore/DPAPI — это происходило на каждую пачку шагов и каждое сохранение. Безопасность не ухудшается существенно: запечатанный ключ и так доступен процессу без участия пользователя. Соединение закрывается перед сменой шифрования, восстановлением после прерванной конвертации, локальным удалением, при ошибке операции и при выходе Windows; на Windows открытый файл нельзя переименовать, поэтому закрытие обязательно. Кеш снимка и правило «публиковать только зафиксированное» прежние.

Декоративная анимация раздела идёт только в окне с фокусом. Схема SQL 2, LAN, Transfer и backup не меняются; режимы и состояния шагомера локальные. Windows и будущий Linux получают шаги только через LAN/backup и датчики не запускают. Измерений мА·ч нет; экономия заявляется как уменьшение работы, а не как измеренный результат.
