# Хранилище и миграции — D062

## Схема 2

Отдельные таблицы `entries`, `products`, `dishes`, `recipes`, `routines`, `schedules`, `notes`, `note_folders`, `estimates`, `local_reminders`, `goal_history`. Строка — один устойчивый агрегат; PRIMARY KEY, позиция списка, payload версии общей модели. Для записей дневника дополнительно date/type/source/deleted и индексы для поиска по дню/типу. Это нормализация на уровне агрегатов, а не полное разложение вложенных исторических снимков/штрихов/ингредиентов на SQL-колонки. Профиль/цели и локальные настройки остаются единственными объектами в metadata; будущие миграции могут разложить вложенные структуры, не меняя формат LAN.

Схема 0 создаётся сразу как 2. Схема 1: прочитать и валидировать Snapshot; внутри одной транзакции создать таблицы, записать агрегаты и metadata, проверить повторное чтение, удалить app_state и установить user_version=2. При любой ошибке rollback оставляет старую базу. Неизвестная версия отвергается. После миграции сохранение меняет только отличающиеся строки; удалённые из снимка строки удаляются физически, tombstones сохраняются как записи.

Порядок списков сохраняется отдельно от ID. GoalHistory не имеет UUID в старой модели: ключ локальной строки — позиция, без изменения переносимого контракта. Отсутствующий singleton metadata в схеме 2 считается повреждением, не пустой базой.

Android SQLCipher и Windows SQLiteMC используют один алгоритм и разные драйверы. Сырой импорт читает схемы 1/2 без миграции исходного файла; экспорт/смена ключа создают схему 2. Старые приложения не умеют читать новую сырую базу: для них использовать `.fiteasy` версии 3. LAN 4/Transfer 3/backup 3 не меняются, Linux сможет реализовать тот же SQL-драйвер.

Проверки: новая/старая/пустая/повреждённая/будущая схема, rollback при прерывании, агрегаты/порядок/tombstones, неизменившиеся строки, SQLCipher plain/encrypted/rekey/raw import. Практический обмен сырой базой Android/Windows остаётся проверкой устройств.
